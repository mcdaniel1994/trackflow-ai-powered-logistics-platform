# Milestone 7 — RAG & Knowledge Base

> **Before you start:** Read [`context.md`](context.md) before writing any code. It defines the
> specific company data, field names, source documents, and constraints for this implementation.
> Other ideas are welcome as long as they fit the objective and direction of the repository.

## 🎯 The Challenge

You already have a working central API and a data pipeline feeding real-time dashboards. Now your
company needs something different: anyone on the commercial team should be able to ask a question
in natural language and get a reliable answer, without manually digging through scattered
documents.

The sales team keeps losing time answering questions from prospects and clients that are already
answered somewhere in an internal document—policies, catalogs, procedures—but nobody can find
them in time. Your tech lead forwards you a **ticket** with the **brief** the commercial team left:
they need an assistant that answers **from a salesperson's perspective**, with the voice and
priorities of the business, not a search box that dumps raw database fragments.

The **ticket** is explicit about the core acceptance criterion: the final answer must always be
generated by a model from the retrieved context—the raw result of the vector database search must
never be returned directly. The solution must also be modularized: each responsibility (preparing
the data, storing the vectors, searching, and generating the answer) must live in its own function,
so the technical team can swap out any piece without touching the others.

### 📚 Complementary knowledge — RAG is not memory

A RAG system doesn't store "memories" of a conversation—it's a **knowledge base** your system
consults before answering. Every time a question comes in, the system searches for the most
relevant fragments of your documents and hands them to the model as context so it can draft the
answer. This is different from conversational memory (what the agent remembers from previous
turns), and both concepts can coexist in the same system but solve different problems.

For this milestone you'll work directly with the Qdrant SDK and FastAPI—no orchestration
frameworks (LangChain, LlamaIndex, etc.). That means you write the four minimum functions
(`setup`, `embed`, `retrieve`, and `query`) yourself, which forces you to understand what each
piece does instead of delegating it to an abstraction.

### 📚 Complementary knowledge — Chunking and similarity thresholds

**Chunking** determines what the retriever can find. A chunk that cuts a policy in half produces
fragments that lack the condition they depend on—the model will hallucinate or refuse to answer.
Chunk by semantic units: a section, a product block, or a procedure step group—not a fixed
character count alone.

**Similarity threshold** is the guardrail against irrelevant context. Top-k alone always returns
k chunks even when none are a good match. Apply a minimum score (cosine similarity or the metric
your embedding model uses) and return **fewer than k**—or zero—when nothing clears the bar. Forcing
bad context into the prompt is worse than admitting you found nothing.

**Two models, two jobs:** the embedding model turns text into vectors for search; the generation
LLM turns retrieved context plus the question into a natural-language answer. You **must** use a
dedicated **embeddings model** for `embed()`—never the same model you call for generation in
`query()`. They have different APIs, output shapes, latency, cost, and failure modes.

For this milestone, the generation provider will likely be DeepSeek because an account and API key
are already available.

## 🌱 How to Start the Project

1. Create a new branch for this milestone.
2. Add Qdrant to `docker-compose.yml` (or use Qdrant Cloud) and confirm connectivity from your
   Python environment. If it fits the project context well, other vector databases can be
   discovered and discussed.
3. Install dependencies with `uv add`—Qdrant client, an embeddings library, the generation LLM
   SDK, FastAPI, etc.
4. Review [`context.md`](context.md), copy the company source documents you must index (policies,
   catalogs, procedures—filenames are company-specific) into `docs/company-knowledge-base/` in
   the monorepo, and point `setup()` at that folder.
5. Implement the four functions in this order:
   `setup → embed → retrieve → query → API → UI → tests`.

Suggested file layout (names may vary; responsibilities must not, unless a better approach is
recommended and discussed):

| Responsibility | Location (indicative) |
|---|---|
| Source knowledge corpus | `docs/company-knowledge-base/` |
| Chunking + indexing | `data/process/rag.py` |
| Retrieval + generation | `data/pipelines/rag.py` |
| HTTP endpoint | `services/routers/` or `services/api/` |
| Query UI | `uis/` |
| Unit tests | `tests/pipelines/test_rag.py` |
| RAG design document | `docs/rag/rag-design.md` |

## 💻 What You Need to Do

### Phase 1 — Data preparation and indexing (`data/process/`)

- [ ] Implement `setup()`: read the source documents from `docs/company-knowledge-base/` (the
  corpus listed in [`context.md`](context.md)), parse them (Markdown, plain text, or the format
  specified in context), and split them into coherent semantic chunks. Each chunk must be a
  self-contained unit—no sentence or rule cut in half.
- [ ] Implement `embed(text: str) -> list[float]`: generate a vector for a single text using a
  dedicated **embeddings model**, not the same model used for generation in `query()`. The same
  `embed()` function is used for chunks at index time and for the user question at query time.
- [ ] Create or recreate the Qdrant collection for your company (collection name from
  [`context.md`](context.md)). Upsert all chunks with:
  - `vector`: output of `embed(chunk_text)`
  - `payload`: at minimum `source_document`, `section`, `company`, `language`, `chunk_index`, and
    `text` (chunk body for prompt assembly)—using the field names from [`context.md`](context.md)
- [ ] Make `setup()` idempotent for development: re-running it should not duplicate points. Use
  deterministic point IDs or a clear-and-reload strategy, and document which you chose.

### Phase 2 — Retrieval and generation pipeline (`data/pipelines/`)

- [ ] Implement
  `retrieve(query: str, *, k: int = 5, min_score: float) -> list[dict]`: embed the query, search
  Qdrant for the top-k nearest neighbors, **filter out** any hit below `min_score`, and return the
  surviving payloads (not raw Qdrant SDK objects).
- [ ] Implement `query(question: str) -> str`: this is the **only** function external consumers
  should call. It orchestrates `retrieve()` → prompt assembly → **generation** LLM call (a
  chat/completion model, not the embeddings model) → final answer string. If `retrieve()` returns
  nothing above the threshold, the model must still respond honestly (for example, that the
  knowledge base has no relevant information) and never invent company facts.
- [ ] Instruct the generation model to answer from a **salesperson's perspective**, using only the
  retrieved context and matching the commercial brief in the ticket.

> **Important:** Field names, collection names, document paths, entity IDs, and domain-specific
> values must match [`context.md`](context.md). A generic implementation that ignores the context
> will not be accepted.

### Phase 3 — Query endpoint (`services/`)

- [ ] Expose `POST /knowledge/query` (or the path specified in context) through FastAPI.
  - Request body: `{ "question": "..." }`
  - Response body: `{ "answer": "..." }`—the model-generated string only
- [ ] Import and call `query()` from `data/pipelines/`. Do not duplicate retrieval or generation
  logic in the router.
- [ ] Never return raw Qdrant search results, chunk lists, or similarity scores to the client.
  Those may be logged server-side for debugging.

### Phase 4 — Query interface (`uis/`)

- [ ] Build a minimal UI (a Next.js page in the Back Office or a small standalone page under
  `uis/`) where a user can type a question, submit it, and see the answer returned by the endpoint.
- [ ] Handle loading and error states—a failed API call must not look like an empty answer.
- [ ] Support light and dark mode if you use the existing Back Office design system.
- [ ] During planning, use the forthcoming query-interface mock image. The query interface should
  be the home page and occupy the top half, with the company's main API data below it. The major
  refactoring plan should also consider reorganizing the Back Office UI because it is becoming
  cluttered.

### Phase 5 — Unit tests (`tests/pipelines/`)

- [ ] Create `tests/pipelines/test_rag.py` (or equivalent) with unit tests for `retrieve()` and
  `query()`.
- [ ] Test `retrieve()` with a mocked Qdrant client or in-memory stub—no live Qdrant is required in
  CI. Verify that results below `min_score` are excluded and fewer than k results can be returned.
- [ ] Mock `retrieve()` and the generation LLM in the `query()` tests. Verify that the function
  returns the model output and does not return raw chunk text without passing through generation.
- [ ] Confirm tests pass with `python -m pytest tests/pipelines/test_rag.py`.

### Phase 6 — RAG design document (`docs/rag/`)

- [ ] Create `docs/rag/rag-design.md` in the monorepo. Another developer should be able to read it
  and understand the RAG stack without digging through the code.
- [ ] **RAG process:** describe the end-to-end implementation flow—from source documents in
  `docs/company-knowledge-base/` through `setup()` → indexing in Qdrant → `retrieve()` at query
  time → prompt assembly → generation LLM → final answer. Include a simple diagram or numbered
  flow if it helps.
- [ ] **Chunking strategy:** document how the company's source documents are split (for example,
  by heading level, semantic section, fixed size with overlap, or a hybrid). Explain **why** that
  strategy fits the corpus: what semantic units it preserves, how it avoids cutting rules or
  conditions in half, and the approximate chunk size or count per document.
- [ ] **Embedding practices:** name the **embeddings model** and **generation model** used (they
  must have different model IDs), confirm use of 4Geeks-provided models where applicable, and
  explain how `embed()` is used consistently at index time and query time. Note the vector
  dimension, Qdrant distance metric, `min_score` threshold and tuning approach, and any text
  normalization or preprocessing.

## ✅ What We Will Evaluate

- [ ] The four minimum functions (`setup`, `embed`, `retrieve`, and `query`) exist, are separated,
  and each has a single responsibility.
- [ ] Source documents live under `docs/company-knowledge-base/` and are what `setup()` indexes.
- [ ] Chunking respects semantic units of the content; no chunk cuts an idea in half.
- [ ] Every chunk stored in Qdrant retains retrievable source metadata (`source_document` and
  `section` at minimum).
- [ ] `embed()` uses a dedicated embeddings model different from the generation model used in
  `query()`.
- [ ] `retrieve()` applies a minimum similarity threshold and does not always force k results.
- [ ] The endpoint's final answer is generated by a model from the retrieved context, not the raw
  vector database result.
- [ ] The endpoint reuses the logic in `data/pipelines/` without duplicating it.
- [ ] The interface allows a user to enter a query and displays the answer obtained from the
  endpoint.
- [ ] Unit tests cover `retrieve()` and `query()` with mocks, and they pass locally.
- [ ] Company-specific implementation values match the assigned [`context.md`](context.md).
- [ ] `docs/rag/rag-design.md` explains and justifies the RAG process, chunking strategy, and
  embedding practices applied, and includes a Mermaid diagram that visually explains the RAG
  process.
